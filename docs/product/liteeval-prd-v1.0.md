# LiteEval 产品需求文档

文档版本 1.0 ｜ 2026年11月1日 ｜ 产品规划与开发验收基线

LiteEval 面向个人开发者及小型 AI Agent 开发团队，通过真实运行轨迹、业务用例集、自动评分和版本回归，判断修改模型、Prompt、工具或 Workflow 后的质量变化，并为上线提供可追溯的验收依据。

本轮建设以现有 0.2.0 后端为基础，优先交付可日常使用的 Web 工作台。产品需求按 P0、P1、P2 分级，正式版本按里程碑验收。本文档的 1.0 是文档版本，不代表软件已经发布 1.0。

## 1 产品目标与范围

### 1.1 需要解决的问题

开发者可以查看 Agent 输出，但难以稳定回答三个问题：一次修改是否改善了业务任务，是否破坏了过去已经正确的任务，以及当前证据是否足以允许上线。生产失败如果只保留为日志，后续修改容易再次引入同一问题。

平台应把每次质量判断关联到明确的 Agent 版本、用例快照、评分器修订和执行证据，使开发者可以重跑、复核、比较，并持续沉淀业务回归集。

### 1.2 目标用户与职责

| 用户 | 核心任务 | 首期使用方式 |
| --- | --- | --- |
| 个人开发者与项目负责人 | 接入 Agent、维护用例、运行实验、判断版本质量 | 单人模式，同一用户完成全部流程 |
| Agent 开发工程师 | 排查失败、修改实现、验证回归 | P1 团队模式的 Editor |
| 评测与业务人员 | 维护期望答案、设计 Rubric、复核质量 | P1 的 Editor 或 Reviewer |
| 项目管理员 | 管理成员、凭据引用、部署和留存策略 | 首期 Owner，团队权限在 P1 加入 |

产品面向团队的长期定位不要求首期采用多租户 SaaS。首期支持单机、自托管、单人使用；小团队能力在稳定闭环后增加。

### 1.3 目标与非目标

P0 目标是让用户仅通过浏览器完成项目初始化、HTTP Agent 配置、Trace 分析、用例维护、实验执行和版本比较。P1 增加人工复核、质量策略和 CI 验收接口，形成可执行的上线验收流程。P2 根据真实需求扩展高级轨迹、多模态、框架接入和规模化部署。

首期范围不包括 Agent Workflow 编辑器、模型训练、通用 APM、自动执行生产发布、计费商城或复杂企业组织管理。平台记录 Prompt 和工具版本信息以解释变化，首期不托管 Prompt 全生命周期。

### 1.4 成功标准

以下为待通过实际验收验证的产品目标，不是现有性能或客户数据。

| 目标 | 测量方法 | 建议验收值 |
| --- | --- | --- |
| 首次接入顺畅 | 在已具备业务 HTTP endpoint 和凭据的前提下，首次配置到首个实验完成 | 30 分钟内完成 20 条确定性用例的流程 |
| 故障转用例高效 | 从 Trace 详情到保存可运行 Case | 3 分钟内完成，不手写 API 请求 |
| 回归结果可解释 | 从回退 Case 定位两侧输出、评分理由和已有证据 | 3 次页面跳转以内 |
| 版本可复现 | 修改数据集后重跑历史实验 | 使用原 Case 与 Evaluator 修订 |
| 关键结果不误判 | 缺失证据、Judge 错误或关键用例未通过 | 不显示质量通过或 Gate PASS |
| 正式版可运维 | 部署后进行重启、恢复、备份还原演练 | 数据与工件关联完整，结果可查 |

### 2.2 优先级定义

P0 是 Web 回归闭环的发布阻塞项。P1 是质量管理与正式版运营所需的下一阶段能力。P2 是由真实业务驱动的扩展，不因出现在愿景中而自动成为 1.0 阻塞项。

| 里程碑 | 建议软件版本 | 交付范围 | 退出条件 |
| --- | --- | --- | --- |
| M1 Web 回归工作台 | 0.3.0 | 本文 P0；六模块；HTTP Agent 完整闭环 | 所有 P0 验收用例通过，真实业务 Agent 走通 |
| M2 质量验收工作流 | 0.4.0 | 人工复核、Eval Spec、Gate、CI 查询、基础成员权限 | Gate 缺证据必阻断，报告可追溯 |
| M3 目标环境验证 | 0.5.0 | 需要的真实 Codex 与 Docker；Judge 校准；运行保障 | 所声明支持的平台和能力有实测证据 |
| M4 正式版 | 1.0.0 | P0 与选定 P1 完整验收、安装升级、备份恢复和文档 | 正式版清单通过，无阻塞缺陷 |

附件中的 V0.1 至 V1.0 表示产品演进层次；本表按当前软件已经是 0.2.0 重新组织里程碑。正式排期在需求确认、技术验证和人员投入明确后制定。

## 3 核心用户流程

### 3.1 首次接入与首次评测

用户进入平台并建立 Owner 会话，创建 Project，在 Settings 配置 HTTP Agent Version，检查 Worker 凭据是否就绪，并主动发送一条试运行请求。成功后选择导入样例或业务 Case，配置评分器，查看提交摘要，运行实验并检查结果。

试运行必须由用户主动触发，提示它会调用业务 Agent；平台不自动试调用有副作用的 endpoint。没有数据集、评分器或在线 Worker 时，向导展示对应行动入口，不允许静默提交后长期等待。

### 3.2 生产失败沉淀为回归用例

用户通过 SDK 或 HTTP 上报生产 Trace，在 Traces 按时间、版本、状态或标签定位问题，查看输入输出及事件证据，点击“加入数据集”，选择 Dataset，补充正确答案、期望工具参数或任务文件要求，设置标签、优先级和失败原因后保存。

来源 Trace 关联必须保留。缺少期望结果时允许保存草稿，但需要答案证据的评分器预检应提示该 Case 无法有效评分。导入的失败输出不能默认填作正确答案。

### 3.3 修改 Agent 后比较版本

用户从已完成的基线实验选择“用新版本重跑”，只替换 Agent Version，保留原快照和评分器修订。新实验完成后进入 Compare，先看回退 Case，再看改善、未评分与未变化 Case，逐项查看两侧输出、证据、理由与数值变化。

数据集或评分器修订不一致时，不允许生成回归胜负结论；页面给出不可比较原因和“按相同快照重新运行”的行动入口。

### 3.4 上线前质量验收

P1 中，负责人发布 Eval Spec，固定测试集版本、评分标准、关键用例与 Gate Policy。候选实验完成后生成 Gate Report，记录使用的策略修订、数据与评分证据。CI 或人工查询该报告，决定是否继续现有发布流程。

平台本身不给生产环境执行发布命令。没有接入 CI 时，BLOCKED 表示平台验收阻断；接入 CI 后，由 CI 根据报告返回值阻断流水线。

## 4 信息架构与通用交互

### 4.1 六个主导航

| 模块 | 主页面与子页面 | 关键行动 |
| --- | --- | --- |
| Overview | 项目质量总览、接入引导 | 查看基线与最近实验、进入失败分析 |
| Traces | 列表、详情、事件面板 | 定位问题、转换为 Case |
| Datasets | 列表、Case 表格、Case 编辑、版本 | 导入、修订、发布与选用测试集 |
| Experiments | 列表、创建、进度、结果、Run、Compare、P1 Gate | 运行、取消、重跑、回归验收 |
| Evaluators | 列表、模板、新建与修订、预览 | 定义规则、测试 Judge、发布评分标准 |
| Settings | 项目信息、Agent 版本、凭据状态、API Key、成员、运行设置 | 接入与管理 |

Project 切换器放在导航顶部。Compare 属于 Experiments；Gate Policy 放在 Settings，Gate Report 属于实验结果；P1 人工复核先作为 Experiments 的筛选视图，不增加第七个主导航。

### 4.2 通用规则

- 中文界面优先，保留 Trace、Case、Run 等术语；时间按用户时区展示，服务端存储 UTC；耗时统一显示 ms 或 s。
- 列表支持 URL 保存筛选、分页和排序。加载、空数据、请求失败、无权限分别展示；切换项目后清空不适用的选择与缓存。
- 状态同时有文字和颜色，键盘可操作表单及主要列表；JSON 面板支持折叠、复制和校验，不要求用户直接编辑原始数据库字段。
- 归档操作说明影响，历史实验始终可读；不能通过浏览器隐藏按钮替代后端权限检查。
- 上次成功数据因断网而过期时标记“数据未更新”，禁止继续显示成实时进度。页面刷新可恢复运行中的实验。
- P0 优先支持桌面 1280 像素及以上视口；小屏能访问核心结果，复杂对比表允许横向滚动。

## 5 模块功能需求

### 5.1 Overview 项目质量总览

**OV 01 P0 时间范围与数据来源。** 默认最近 7 天，支持 24 小时、7 天、30 天和自定义。生产 Trace 与 Eval Run 分区统计；默认不把评测调用计入生产流量。验收时同一批评测运行不能抬高生产 Trace 数量。

**OV 02 P0 运行概况。** 展示 Trace 数、运行成功率、成功样本平均延迟、已上报成本及覆盖率。失败 Trace 数可点入列表。成本缺失显示“未上报”，不同币种分开展示，不能加成一个金额。

**OV 03 P0 评测质量。** 展示用户选定的基线实验与最近候选实验，标明 Dataset Snapshot、Evaluator 修订和样本数，显示质量通过率、评分覆盖率及最近 Compare。不同测试集的分数不直接拼成趋势，不生成无定义的“Agent 总分”。

**OV 04 P0 最近任务与引导。** 展示最近实验、失败 Case 和 Worker 状态。空项目按接入、建集、评分、实验顺序引导。尚未配置基线时显示选择入口，不能用任意最近实验冒充正式基线。

### 5.2 Traces 轨迹分析

**TR 01 P0 查询。** 列表展示时间、Trace ID、来源、Agent 标签、状态、耗时、token、成本和覆盖等级。支持时间、来源、状态、Agent 版本、标签与 ID/输入摘要检索。输入文本检索只对已记录的可索引内容生效，不能承诺搜索关闭采集的内容。

**TR 02 P0 详情。** 顶部显示输入、最终输出、状态和来源；中部显示按 parent_id 构建的事件树和时间轴；侧面板展示单事件输入输出、参数、错误与 attributes。没有时间戳的事件按 sequence 展示，不能编造耗时。

**TR 03 P0 证据完整性。** 展示 output_only、reported_spans、full_harness 的中文解释；显式上报的 span 不等于自动捕获全部调用。事件缺父节点、时间异常或未知类型时可阅读原始数据，并提示不完整。普通事件和原始 JSONL 中都不展示内部模型思考为已采集能力。

**TR 04 P0 转 Case。** 选择目标 Dataset、调整输入、填写 expected、标签、优先级、critical 标记和问题描述。保留 source_trace_id；同一 Trace 重复转换时提示现有 Case，用户仍可明确创建另一测试情景。Eval Trace 详情跳转已有 Case，首期不从 Eval Trace 再转换。

**TR 05 P1 问题管理。** 支持 failure 标签、责任人、复核记录和关联修复版本；失败原因包括答案、工具、轨迹、执行异常及数据问题。人工标注与 Agent 执行状态独立保存。

### 5.3 Datasets 与 Case 管理

**DS 01 P0 数据集。** 新建、改名、描述、标签及归档；列表显示有效 Case 数、最近更新和最近实验。归档后不能用于新实验，历史引用不受影响。首期不物理删除已有实验引用的数据。

**DS 02 P0 Case 编辑。** 字段包括 input、expected、标题、category、tags、priority、critical、metadata 和来源。编辑生成新修订；用户能查看修订号与变化。归档 Case 后不进入下一次快照，历史快照仍保留原修订。

**DS 03 P0 冲突保护。** 保存必须携带 base_revision。若其他页面已修改，返回冲突并展示最新版本，禁止最后一次写入静默覆盖。旧 Case 没有新字段时以明确默认值展示，保留原 metadata。

Case 表单默认 title 最长 120 字，tags 最多 20 个且每个最长 32 字，priority 为 high、normal、low，默认 normal；critical 为布尔值，默认 false。input 必须为 JSON 对象，expected 可为 JSON 值或留空，metadata 必须为对象。新增评测字段存入结构化 metadata 并进入修订快照；已有 category、severity 等内容继续保留。

**DS 04 P0 导入导出。** JSON/CSV 上传后先校验并预览，显示行号、字段错误和有效条数；整批通过才入库，不进行部分成功。导出 JSON/CSV 均为新增界面能力，其中 CSV 服务端导出为后端增量需求。P0 仍受 8 MB API 请求体、单批最多 10000 条等现有限制，以较小上限为准；实际可提交大小需计算序列化后的字节数。

**DS 05 P0 快照可见。** 每次实验展示冻结的 Case 列表、修订和内容哈希。修改 Dataset 不改变历史实验；比较入口优先提供“从基线重跑”。P0 不要求用户手动维护一套额外版本命名体系。

**DS 06 P1 发布版本。** 将 Case 修订集合发布为有名称的 Dataset Version，例如 support-regression 2026 11，保存发布说明与 snapshot_hash。已发布内容不可编辑；后续修改进入草稿并可再次发布。Dataset Version 与实验自动快照复用相同内容模型。

**DS 07 P1 适用范围。** 可为评分器绑定 Case 类别或明确子集，提交时冻结 applicable Case 集合。只有提交前确定的不适用项才可排除；证据缺失、Agent 失败或 Judge 错误不得被改成“不适用”来提高通过率。

### 5.4 Evaluators 评分配置

**EV 01 P0 配置表单。** 展示现有 12 类评分器，按答案规则、工具、性能成本、最终状态和 Judge 分组。每项说明需要的证据、支持字段与示例。JSON Schema 只允许现有受支持子集，未知关键字在保存前报错。

**EV 02 P0 不可变修订。** 用户编辑评分器时创建新修订并保留旧修订；实验始终固定 revision_id。归档只阻止新实验选择。界面可用稳定名称聚合多次修订，不能原地修改历史配置。

**EV 03 P0 预览。** 选择现有 Run 或粘贴测试输入输出，先展示将使用的证据，再点击评分。Judge 预览提示会消耗模型额度，保存模型、配置、结果与原始回复引用；失败说明是凭据、协议、输出格式还是超时。预览不会自动写入已有实验的 scores。

**EV 04 P0 Judge 与模板。** 支持 rubric、模型配置引用、二值或连续尺度、阈值、方向、是否包含轨迹。Task Success、Answer Correctness、Tool Correctness 等作为可编辑模板；模板必须绑定实际规则或 Judge 配置，不能只创建好听的指标名。

**EV 05 P1 幻觉与轨迹模板。** 幻觉检查需提供版本化参考答案、检索证据或允许使用的事实来源；仅依赖 Judge 常识的评分明确标记为主观判断。轨迹合理性依赖足够的事件证据，缺少轨迹返回 abstain。复杂依赖、顺序约束和状态机评分在 P2 扩展。

**EV 06 P1 人工评测。** 保存 reviewer、目标 Run、维度、结论、理由、标注规范版本和时间；支持复核争议。人工记录不覆盖原机器分数。只有指定的评测集才能用于 Judge 校准；记录样本量、一致率和分歧分布，不预设模型已达到可靠标准。

### 5.5 Experiments 执行与比较

**EX 01 P0 创建向导。** 依次选择 Project、Agent Version、Dataset、Evaluator 和运行参数。提交前展示 Case 数、关键 Case 数、证据缺失统计、版本摘要与潜在调用数量。只有配置了单价或预算参数时才提供有依据的费用估算；未配置时显示未知。

**EX 02 P0 预检。** 必检项目一致性、非空用例、评分器可用性、配置结构和 Worker 凭据状态。预检只检查配置与存在性，不自动调用业务 Agent。所选必需评分器明确要求 expected、且没有评分器常量可替代时，只要适用 Case 存在缺失即阻止标准运行；用户可明确以“诊断运行”提交，结果不得用于 Gate。尚不能提前确定的 HTTP 轨迹完整性作为警告，实际评分仍按证据返回 abstain。

**EX 03 P0 提交与幂等。** 为一次用户提交生成并保存 Idempotency-Key，网络重试复用相同 key；相同 key 不同请求提示冲突。按钮重复点击不产生多个实验。提交摘要记录名称、描述、Agent 版本、快照和运行配置。

**EX 04 P0 进度与状态。** 展示 queued、running、completed、failed、cancelled 以及取消申请中的 UI 状态；Run 展示等待、执行、重试、完成、失败、超时和取消。进度分子为已终结 Run，分母为冻结 Case 总数；显示成功、失败和未评分拆分。

**EX 05 P0 取消与恢复。** 取消后说明已请求并停止新任务，远端 HTTP 可能继续运行至超时。只有服务端确认后显示 cancelled。刷新页面不重复提交；Worker 崩溃时提示等待接管，已提交结果不能被旧 Worker 覆盖。

**EX 06 P0 结果页。** 显示执行成功率、质量通过率、评分覆盖率、评分状态分布、平均延迟、usage、分币种成本和样本数。Case 表格支持 fail、unscored、cancelled 筛选。Run 详情可查看输入、输出、评分理由、证据 Event、Attempt、轨迹、文件和 patch。

**EX 07 P0 重跑。** “同条件重跑”保留快照、评分器和配置；“测试新 Agent 版本”只替换 Agent Version；“使用当前数据重新创建”生成新快照且明确不保证与旧实验可比较。三种动作必须用不同文案。

**EX 08 P0 Compare。** 检查项目、快照、Case 修订和评分器修订。通过后显示整体指标差值和 improved、regressed、same、unscored 数量，默认优先回退与未评分。Case 并排展示两侧结果，混合改善与回退按 regressed 计且带 mixed 提示。

**EX 09 P0 比较边界。** 连续分数未跨过阈值时 Case 可能仍为 same，数值变化照常显示。单次 LLM 运行结果不显示为统计显著。环境、并发、资源或模型服务变化时，性能对比展示条件差异；不提供无条件“更快”的结论。

**EX 10 P1 独立重评分。** 复用已经保存的输出或最终状态进行新的 Scoring Session，绑定新评分器修订；禁止覆盖旧 scores。新的评分结果只能与相同评分器修订的结果比较，并明确不代表 Agent 已重新执行。

### 5.6 Settings 与身份管理

**ST 01 P0 浏览器登录。** 单人模式通过部署者设置的 Owner 凭据建立服务端会话；浏览器只持有 HttpOnly 会话 Cookie，不保存管理员 API Token。退出和凭据轮换可撤销会话。未登录访问业务页面进入登录流程。

**ST 02 P0 Agent 配置。** 管理 HTTP Agent Version、环境变量引用及模型、Prompt、Tool、Workflow 的可选版本标识。修改生成新 Agent Version。凭据仅在 Worker 端使用；页面只显示变量名和就绪状态，不读取或回显明文。

**ST 03 P0 项目密钥。** 创建、命名、查看标识和撤销；明文仅签发时显示一次。SDK 使用项目密钥；网页日常操作使用会话。撤销后新的 API 请求立即失效。

**ST 04 P0 运行状态。** 显示 API/Worker 最近心跳、队列等待、数据库与工件路径的配置摘要；普通用户不获得主机敏感路径或凭据值。实际工作目录、镜像和验证命令只能由受信任管理员配置。

**ST 05 P1 团队权限。** Owner 管理成员与密钥；Editor 管理数据和实验；Reviewer 提交人工标注；Viewer 只读。权限按 Project 在服务端检查。项目 API Key 的读写权限与高权限配置权限分开，保持旧 SDK 的兼容迁移路径。

**ST 06 P1 留存与审计。** 配置生产 Trace 与非引用工件留存，展示删除预演和审计事件。被快照、基线、Gate 或复核引用的证据按引用策略保留；不能删除证据后仍显示报告完整可验证。

## 6 Eval Spec 与上线验收

### 6.1 Eval Spec

P1 将质量要求表示为不可变 Eval Spec Revision，包含业务说明、Dataset Version 或快照、Evaluator 修订集合、关键用例选择、运行环境约束、最小样本量和 Gate Policy Revision。修改任一项创建新修订。

Spec 定义验收口径，Experiment 记录实际执行，Gate Report 记录本次判断。三者不能合并为一个可随时编辑的实验配置。

### 6.2 Gate 状态与规则

Gate Report 的状态为 PENDING、PASS 或 BLOCKED。BLOCKED 的原因分为 threshold_failed、insufficient_evidence、incomparable、execution_incomplete、policy_invalid 和 required_review_missing。没有足够证据时必须阻断，不能默认通过。

| 条件 | 示例策略 | 计算与阻断规则 |
| --- | --- | --- |
| 实验完整 | 所有必需 Case 执行结束 | failed、cancelled 或仍执行中的实验不能 PASS |
| 样本量 | 总 Case 至少 30 | 30 为建议初值；不足时阻断并显示实际数量 |
| Task Success | 至少 90% | 任务成功 Case / 全部必需 Case，不能排除执行失败 |
| Critical Cases | 100% 通过 | critical Case 必须全部通过且证据完整；未配置关键 Case 时策略校验失败 |
| Tool Accuracy | 至少 95% | 工具评分 pass / Spec 中冻结的 applicable Case 总数；缺证据仍在分母 |
| 评分覆盖率 | 至少 95% 或更严格值 | 有效 pass/fail Case / 全部必需 Case；关键集要求 100% |
| 回退限制 | critical 回退为 0 | 依赖严格可比较的基线；无法比较则阻断相应条件 |
| 成本与延迟 | 按业务配置 | 成本要求固定币种和覆盖率；延迟限定相同环境和指标定义 |

建议模板值必须由业务负责人调整后发布。只有回归小集的项目可配置更小最小样本量，并在报告中展示该限制；平台不能据此宣称有统计显著性。

### 6.3 示例与审计

示例：候选实验 100 个必需 Case 中 92 个任务成功，工具适用集 50 个中 48 个通过，20 个关键 Case 中 19 个通过，结果为 BLOCKED：任务成功率 92% 通过，工具正确率 96% 通过，关键 Case 95% 未达到 100%。若关键 Case 的缺失证据被人工移出分母，仍不得通过该策略。

Gate Report 保存 Spec/Policy 修订、实验、基线、快照、评分器、计数、分母、证据链接和生成时间。策略发布后再修改不影响旧报告。P1 默认不允许人工把 BLOCKED 改成 PASS；如后续支持业务豁免，应另记决策、人员和理由，保留原报告。

## 7 数据与指标口径

### 7.1 核心对象

| 对象 | 必要属性与关系 | 变更规则 |
| --- | --- | --- |
| Project | 名称、描述、成员与设置 | 元数据可编辑，权限有审计 |
| Agent Version | 执行配置、config_hash、外部版本标识 | 执行配置不可变 |
| Trace 与 Event | 来源、输入输出、事件、metadata、采集等级 | 业务采集记录保留原始证据 |
| Case Revision | input、expected、metadata、source_trace_id | 内容修改创建新修订 |
| Dataset Snapshot | Case ID、revision、hash、有序集合 | 不可变；归档不影响已有引用 |
| Evaluator Revision | kind、config、hash、证据要求 | 不可变 |
| Experiment 与 Run | 冻结快照、Agent、评分器、运行配置 | 实验终结后原始结果不可覆盖 |
| Attempt 与 Score | 重试历史、输出、usage、outcome、reason | Judge 重试留原始记录；新评分会话独立 |
| Artifact | 项目、来源、hash、类型、大小 | 下载鉴权，完整性校验 |
| Spec 与 Gate Report | 版本化标准及判定证据 | 报告不可变 |

### 7.2 必须区分的指标

| 指标 | 定义 | 界面要求 |
| --- | --- | --- |
| 执行成功率 | succeeded Run / 全部快照 Case | 不命名为任务成功率 |
| 任务成功率 | Spec 指定的任务评分器 pass Case / 全部必需任务 Case | 必须指定具体任务评分器，不与执行成功率或全部规则通过率混用 |
| 质量通过率 | 所有必需评分器通过的 Case / 全部快照 Case | 默认主质量指标，与当前 success_rate 一致 |
| 已评分通过率 | Case pass / Case pass 加 Case fail | 必须同时展示评分覆盖率 |
| 评分覆盖率 | 有效 Case pass/fail / 全部快照 Case | abstain/error/执行失败不计入有效评分 |
| 单评分器通过率 | pass / pass 加 fail | 保留现有 reports 语义，不能直接冒充 Gate 完整分母指标 |
| 平均执行耗时 | 成功 Run 的端到端执行耗时均值 | 包含环境生命周期，不含 Judge；附样本数 |
| 成本 | 最终 Run 与全部 Attempt 分别按币种汇总 | 重试成本、缺失覆盖和 Judge 成本分开展示 |
| 改善与回退 | 相同快照和评分器下的 Case 分类 | 任一回退优先，缺失证据不得记改善 |

P0 不新增模糊的综合 Eval Score。P1 如需要加权评分，必须冻结维度、权重、尺度和缺失处理，并保留原始指标，不用于掩盖关键 Case 失败。

## 8 非功能要求

### 8.1 性能与容量

验收基准建议为 4 核、8 GB 内存、SSD 单机，10000 条 Trace、1000 Case、5 个浏览器会话，单实验并发 8。列表每页 50 条，常用查询 API p95 不高于 1 秒，核心页面初次可用不高于 3 秒；均不包含模型推理和外部网络延迟。实现后需记录操作系统、数据形态和测量方法。

运行页 P0 以约 2 秒轮询进度摘要、失焦退避、结束停止为准；不能反复拉取所有输出和工件。大事件、长输出与工件按需加载。容量目标不代表当前已达到，也不沿用模拟 Agent 的吞吐作为真实模型性能。

### 8.2 可靠性与恢复

API 与 Worker 重启不能丢失已提交实验。单机租约和恢复语义继续保留；杀死 Worker 后等待租约过期接管，已终结 Run 不重复执行。对远端执行维持至少一次调用语义，接入文档明确幂等责任。异常、取消与重试均有可检索记录。

正式版需完成数据库加工件一致备份、还原、升级前备份和迁移失败恢复演练。数据迁移不能混跑不兼容 schema 的旧 Worker。默认不承诺多机高可用。

### 8.3 安全与数据保护

浏览器会话需要 HttpOnly、SameSite、CSRF 防护与过期撤销；HTTPS 部署使用 Secure Cookie。业务 endpoint 和验证命令仅受信任配置者可改。机密不写入前端存储或日志；对原始 JSONL、patch 和文件证据保持鉴权及下载隔离，明确它们可能含业务敏感内容。

Trace 输入输出按文本或 JSON 渲染，不能执行其中 HTML/脚本。文件预览不执行代码，HTML 工件以下载或隔离模式查看。跨项目资源、ID 猜测、工件访问和导出都要执行服务端作用域校验。

### 8.4 兼容与可用性

优先支持开发者使用的 Windows 本机 HTTP 工作流，以及 Linux 单机正式部署；浏览器支持验收时的 Chrome、Edge 最近两个稳定大版本。Codex、Docker 和进程清理按实际平台独立声明支持等级，不使用替身通过来代替真实验收。

保留已有 /v1 API、CLI 和 SDK 的兼容性；新增结构使用版本与可选字段，不静默改变旧指标口径。

## 9 验收场景

以下场景需要在交付中映射到测试或人工验收记录。P0 无关的高级能力不能成为首期验收阻塞项。

| 编号 | 级别 | 场景 | 预期结果 |
| --- | --- | --- | --- |
| AC 01 | P0 | 创建项目并接入一个真实 HTTP Agent | 能主动试运行，凭据不回显 |
| AC 02 | P0 | SDK 上报嵌套事件 | 树形父子关系正确，缺失字段有说明 |
| AC 03 | P0 | 失败 Trace 转 Case | 保留来源，可填写独立 expected |
| AC 04 | P0 | 100 条 CSV 中一行非法 | 标行号，整批不入库 |
| AC 05 | P0 | 两个页面编辑同一 Case | 旧 base_revision 保存返回冲突 |
| AC 06 | P0 | 修改 Case 后重跑旧实验 | 原快照内容保持不变 |
| AC 07 | P0 | 重复点击与提交超时重试 | 只产生同一幂等实验 |
| AC 08 | P0 | 缺 expected 或轨迹 | 展示预检和 abstain，不作为质量通过 |
| AC 09 | P0 | Agent 执行失败、Judge 出错 | 执行状态与评分状态分开展示 |
| AC 10 | P0 | Judge 非法 JSON 后重试 | 留原始结果，不再次调用 Agent |
| AC 11 | P0 | queued/running 时取消 | 显示取消申请，最终状态来自后端 |
| AC 12 | P0 | Worker 崩溃后接管 | 已提交结果不重跑，旧 Worker 不能覆盖 |
| AC 13 | P0 | 同快照新 Agent 比较 | Case 分类与两侧证据一致 |
| AC 14 | P0 | 不同评分器修订比较 | 显示不可比较及修复入口 |
| AC 15 | P0 | CNY、USD 与未上报成本混合 | 分币种与覆盖展示，不误算为零 |
| AC 16 | P0 | 切换项目或访问他项目 Artifact | 缓存隔离，服务端拒绝越权 |
| AC 17 | P0 | 归档 Case/Dataset/Evaluator | 不影响历史实验与报告读取 |
| AC 18 | P1 | 关键 Case abstain 或取消 | Gate BLOCKED 并说明证据不足 |
| AC 19 | P1 | 人工与机器评分分歧 | 两份记录均保留，按策略决定复核 |
| AC 20 | P1 | 策略修改后查看历史 Gate | 仍绑定原策略修订及原判定 |
| AC 21 | P1 | CI 查询尚未完成或不可比较结果 | 返回明确等待/阻断原因，不能 PASS |
| AC 22 | P1 | 备份后在新目录恢复 | Case、实验、工件 hash 与报告完整 |

## 10 范围决策与发布条件

首期默认选择单人自托管、HTTP Agent 优先、中文桌面工作台、服务端会话、单机 SQLite、本地工件与轮询进度。团队权限、人工评测和 Gate 在 P1；OTel、复杂轨迹规则、音视频评分、分布式队列和对象存储在 P2。

正式发布前，项目负责人确认三个具体范围：第一批业务 Agent 与关键用例；是否将真实 Codex/Docker 列为正式支持；Gate 阈值、人工复核和最小样本量。未纳入本轮正式支持的能力保留清晰状态，不影响已验收的 HTTP 工作流发布。
